# Turso Remote DB Driver Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let Plexus run against a remote Turso Cloud database by accepting `libsql://` `DATABASE_URL`s, driven entirely through `@tursodatabase/serverless` (compat mode), with zero changes outside the DB connection layer.

**Architecture:** Turso *is* SQLite remotely served over Hrana-over-HTTP, so the existing `sqlite` dialect and Drizzle schema are reused verbatim. Only `packages/backend/src/db/client.ts` — the single gateway every repository/service reaches via `getDatabase()`/`getSchema()` — learns one new URL scheme: it builds an `@tursodatabase/serverless/compat` client (a drop-in `@libsql/client` shape) wrapped by `drizzle-orm/libsql`. Local `sqlite://`, PGlite, and Postgres paths remain byte-for-byte unchanged.

**Tech Stack:** Bun, Fastify, Drizzle ORM `^0.45.2`, `@tursodatabase/serverless@1.4.0` (pure fetch, no native deps — safe under Bun and `bun compile` binaries), Vitest.

**Spec:** Approved design delivered in chat 2026-08-27 (session). Decisions locked by the user: credentials via `DATABASE_URL=libsql://...` + `TURSO_AUTH_TOKEN` env (fallback `?authToken=` URL param); v1 is plain-remote only (no embedded replica/sync); live Turso credentials will be made available for end-to-end verification.

```ts
export function parseConnectionString(uri: string): {
  dialect: SupportedDialect;
  connectionString: string;
} {
  if (uri.startsWith('sqlite://')) {
    // …existing body unchanged…
  } else if (uri.startsWith('libsql://')) {
    // Turso Cloud / libSQL remote server — still the SQLite dialect, reached
    // over Hrana HTTP via @tursodatabase/serverless/compat (see below).
    return { dialect: 'sqlite', connectionString: uri };
  } else if (uri.startsWith('postgres://') || uri.startsWith('postgresql://')) {
    return { dialect: 'postgres', connectionString: uri };
  }
  throw new Error(
    `Invalid database URI: must start with sqlite://, libsql:// or postgres://. Got: ${uri}`
  );
}
```

(Bodies of the untouched branches stay exactly as they are today, including the `:memory:` normalization.)

## Risks & pre-agreed responses

1. **Compat-mode type mismatch** against `drizzle-orm/libsql`'s expected client interface → handled in Task 3 with a single narrow cast (`as unknown as Parameters<typeof drizzleLibSql>[0]`). Structural (runtime) compatibility is what matters; compat mode implements the `@libsql/client` API surface including `execute`, `batch`, and `transaction`.
2. **Interactive transactions over Hrana** (used by `config-repository.ts:985/:1693`, `mcp-key-migration.ts:63`) — Task 5 Step 1 exercises the genuine path. If Turso errors here, the fallback (pre-approved, still within minimal-changes) is pinning those three call sites behind a batch-based equivalent — decide WITH the user at that point, not speculatively.
3. **Migration runner over HTTP** — statement-by-statement execution makes first boot slower (network RTTs) but correct; acceptable one-time cost. Fatal SQL errors would be fixed in `migrate.ts` with the user informed.
4. **Latency ceiling on hot-path queries** — deliberately accepted for v1 (plain remote). Marked in code with the `ponytail:` comment; the named upgrade path is an embedded replica via `@tursodatabase/database`.
